# AI agents now build websites. Ours makes sure people can actually use them.

![innovationlab](https://img.shields.io/badge/innovationlab-3D8BD3)
![hackathon](https://img.shields.io/badge/hackathon-5F43F1)

AI agents are shipping websites at machine speed, and most of those pages break for people who use screen readers or keyboards. Our agent is a pre-ship gate other agents hire. Send a URL and it scans the page, walks it like a keyboard user, applies fixes that are re-checked to make sure nothing got worse, and returns a signed log of exactly what was tested. It's also honest about what wasn't tested: it never claims a page meets the standard, because automated tools catch less than half of accessibility problems. Builder agents ship better pages, and disabled users get sites that work.

## The problem

Pages generated by agents often ship with unlabelled buttons, missing alt text, low-contrast text and keyboard traps. A screen reader hears "button. button. image." A keyboard user gets stuck. Nobody checks before the page goes live.

## Agents

A11y Gate is one uAgents Bureau with four agents. Talk to the lead; it hires the other three.

| Agent | Role | Address |
|---|---|---|
| lead (`a11y_gate`) | Chat Protocol + Payment Protocol, mailbox | `<LEAD_ADDRESS>` |
| scanner | axe-core 4.14.0 in Playwright Chromium | `<SCANNER_ADDRESS>` |
| walker | deterministic keyboard walk (up to 50 Tab presses) | `<WALKER_ADDRESS>` |
| fixer | deterministic, rule-based patches (no LLM) | `<FIXER_ADDRESS>` |

## Quick start (local run)

```bash
python -m venv .venv && source .venv/Scripts/activate   # on Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt && playwright install chromium
export LEAD_SEED=... SCANNER_SEED=... WALKER_SEED=... FIXER_SEED=... RECEIPT_KEY_HEX=...
python -m agents.lead        # prints the four agent addresses and an Inspector link
python -m pytest -q
```

Connect the lead's mailbox from the Inspector link, then chat with it from ASI:One.

Reproduce an empty result: send `check https://example.com`. You get zero automated violations, the keyboard-walk summary, the full disclaimer and the list of criteria that were not tested.
Reproduce a blocked URL: send `check http://169.254.169.254/`. The metadata address is refused before any content loads and you get an error report.

## Usage

Send a chat message to the lead (for example from ASI:One):

- `check <url>`: free automated scan plus keyboard walk. 5 per sender per UTC day.
- `fix <url>`: patch rechecked on the page source with scripts off (page scripts are not re-run) plus signed scan log, 0.5 TEST FET on Dorado testnet. Live charging is off.

`fix` uses the Payment Protocol (seller role). The lead sends a `RequestPayment` for 0.5 TEST FET (`fet_direct`) to its own wallet address, with the job id as `reference` and a 300 s deadline. The buyer pays on Dorado **with the tx memo set to the reference** and sends `CommitPayment` with the tx hash and that reference. The lead checks the tx on chain (successful, memo equals the reference, a bank send of at least 0.5 TEST FET to its address, hash never used before). Only then does it run the fix, and it replies `CompletePayment` after the report is delivered. A tx that is not indexed yet gets "transaction not found yet - resend CommitPayment". Any other mismatch gets a "Payment not accepted: <reason>" chat line. In both cases the reference stays open until its deadline, so fix it and resend `CommitPayment`. In-memory; a restart mid-job loses the paid job (testnet). A reference is consumed once, by a verified payment, and only the sender who asked can use it. `CancelPayment` is sent only when a reference closes unpaid: at the deadline ("payment window expired", which also reaches chat-only callers) or after `RejectPayment`.

Set `PAYMENT_ENABLED=0` to switch payment off for the event: `fix` then runs free, counts against the 5 free scans per day, and its reply is labelled "payment disabled for the event". The default is `1`.

Input is a single public http(s) URL. No crawling, no pasted HTML. Each page gets 30 s and 2 MB at most.

## Limits

Every scan report ends with this disclaimer, with the numbers filled in:

> "Automated scan result: X violations found across Y tested WCAG 2.2 AA success criteria. Z criteria require manual/human testing and were NOT evaluated. This is not a WCAG conformance determination or legal compliance certification. Suggested code changes are unreviewed and must be checked by a developer before use."

Automated tools find less than half of accessibility problems. In the GOV.UK GDS accessibility audit, the best automated tool found roughly 40% of the known issues; the rest needs a human. Logical focus order and obscured focus are reported as needing review, never as failures. Nothing is stored; logs hold only rule ids, hashes and job ids. Pages that redirect are scanned at the original URL; relative assets may not load, so results for them can be incomplete.

## Verify a scan log

Every `fix` reply carries an "Automated Scan Log": a JSON payload and an Ed25519 signature over its exact bytes. The payload binds the URL, the SHA-256 of the HTML we scanned, the time, the fix outcomes and the disclaimer. It is valid for that exact input at that time only.

Our published receipt public key (raw Ed25519, hex):

`1cbce8c5af4a0f8c463d3273046fef03d59b11ca8f7f337c046fc71592475f2e`

Always check the signature against this published key. Never trust the key embedded in a receipt: anyone can sign a forged log with their own key and embed it.

```python
from gate.models import Receipt
from gate.receipt import verify_receipt
verify_receipt(Receipt(payload_json=payload, signature_hex=sig, public_key_hex=PUBLISHED_KEY), PUBLISHED_KEY)
```

## Configuration

Secrets come from environment variables only (names below; never commit values):

`LEAD_SEED`, `SCANNER_SEED`, `WALKER_SEED`, `FIXER_SEED`, `RECEIPT_KEY_HEX`, `PAYMENT_ENABLED` (optional, `0` turns payment off), `LEAD_ADDRESS`, `BUYER_SEED`, `BUYER_WALLET_MNEMONIC`

The deployed container needs the first five. `PAYMENT_ENABLED` is optional (default `1`). `LEAD_ADDRESS` and `BUYER_*` are for the local demo buyer only.

## Deploy (Fly.io, always on)

The container renders attacker-supplied URLs, so `deploy/entrypoint.sh` starts as root, loads an nftables egress firewall that blocks the app user from private, loopback, link-local, metadata and Fly 6PN ranges (DNS to the resolver in `/etc/resolv.conf` excepted), and only then drops to `pwuser` and starts `python3 -m agents.lead`. If the firewall fails to load, the app does not start.

1. Install flyctl: <https://fly.io/docs/flyctl/install/>
2. `fly auth login`
3. Edit `fly.toml` and replace `a11y-gate-<CHANGE_ME>` with your app name, then `fly launch --no-deploy --copy-config`
4. `fly secrets set LEAD_SEED=... SCANNER_SEED=... WALKER_SEED=... FIXER_SEED=... RECEIPT_KEY_HEX=...`
5. `fly deploy`
6. `fly logs` shows the four agent addresses. Copy them into the table above.
7. Connect the mailbox once, before or after deploying: run the lead locally with the production `LEAD_SEED` (`python -m agents.lead`), open its Inspector link, click **Connect**, choose **Mailbox**, stop it, then `fly deploy`. The mailbox belongs to the agent address, so the deployed lead picks it up. The Inspector is lead-only; the three subagents run with it off.
   - Fallback, if the local connect is not possible: the agent server listens on IPv4 only, so bridge it for the session. Terminal A: `fly ssh console -C "socat TCP6-LISTEN:8001,bind=[::],fork,reuseaddr TCP4:127.0.0.1:8000"`. Terminal B: `fly proxy 8000:8001`. Open the Inspector link from the logs, click **Connect**, choose **Mailbox**, then close both terminals.
8. Check the firewall: `fly ssh console -C /app/deploy/egress-check.sh` (exits non-zero on any unexpected result).
9. In ASI:One, send `check https://example.com` to the lead. Expect a reply within 60 s and the Agentverse profile showing Active.
